# Nightlink 0.8.22-rc.3 — local startup connection candidate

Tracking: [#56](https://github.com/njsnowman/nightlink/issues/56), [PR #52](https://github.com/njsnowman/nightlink/pull/52). See [changelog](../CHANGELOG.md) and [startup behavior](../STARTUP_CONNECTION.md). Application source: 43c4012b0f56b609874d1a6bccca2aaa1df791d1. Later commits only add validation documentation.

## Scope

Optional startup connection to the last successfully synchronized radio. Default off. Windows main-frame bridge persists only the enabled flag and selected device descriptor; Bluetooth uses exact device ID and USB uses serial/vendor/product. USB devices with no hardware serial require manual selection. Three attempts with 5s and 15s waits; Cancel, manual connection, Disconnect and disabling cancel startup retries. Synchronization errors stop startup retry; ready opens Overview. Existing synchronization and per-radio history remain authoritative.

## Isolated validation

23 startup-desktop, serial and recovery unit tests passed. startup-connect.browser.test.cjs passed for startup success/sync, three failures, cancellation, sync-error pause and opt-in Settings. navigation.browser.test.cjs passed with synthetic 350 contacts/20 channels across viewport/compact checks.

Final app.asar with Electron 42.11.12 passed startup-connect.native.test.cjs: real packaged bridge with synthetic Bluetooth discovery chose the exact saved device despite a same-name alternative; synthetic synchronization opened Overview; opt-out persisted after reload and prevented startup. No physical Bluetooth APIs were invoked by this fixture. navigation.native.test.cjs passed at 760x528, 760x600, 920x700 and 1320x860 in both compact states.

All profiles were isolated. No production profile changes, peer sends, adverts, radio settings writes or physical-radio validation. Physical Bluetooth/USB startup behavior remains to be confirmed. Existing physical nonempty queue recovery acceptance remains open under #49; this candidate does not claim to fix it.
