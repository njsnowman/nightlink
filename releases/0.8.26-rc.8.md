# Nightlink 0.8.26-rc.8 - Bounded core read recovery

Tracking [#109](https://github.com/njsnowman/nightlink/issues/109), [PR #110](https://github.com/njsnowman/nightlink/pull/110).

Only the exact read-only queries get name, get tx, get lat, get lon and get radio may recover from a reply timeout, with a maximum of three transmissions. Each retry uses a fresh paced companion-clock timestamp. Queued messages are drained before recovery, and a bounded quiet interval consumes duplicate CLI replies before another query starts. Connection, owner and authorization guards remain active throughout. Exhausted attempts invalidate the uncertain session. Configuration writes, advanced commands and optional firmware queries never retry automatically.

Firmware CLI replies lack request IDs. Serialization, queue draining and a quiet interval reduce late-reply ambiguity; they cannot add correlation that firmware does not provide. Existing preflight/readback safeguards remain required before treating configuration writes as verified.

Physical rc.7 follow-up: after companion reconnection, admin login and name read succeeded; TX-power read then timed out. Bounded read recovery addresses this observed failure mode without changing radio settings. Regression tests verify a lost reply followed by recovery, duplicate consumption while serialization remains held, three-attempt exhaustion, and prevention of write retries even when recovery is requested.
