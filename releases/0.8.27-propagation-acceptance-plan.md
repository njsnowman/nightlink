# Nightlink 0.8.27 RF Propagation Monitor physical acceptance plan

Prepared October 31, 2026 for owner execution. This is a test plan, not evidence. Record each result with local times in [propagation monitor validation](propagation-monitor-validation.md), and keep physical results separate from simulated results. The detection model, assumptions and known false positives are in [docs/propagation-monitor.md](../docs/propagation-monitor.md).

Run the tests in the order below. Stop a test at the first unexpected result, record it as observed, and do not retry automatically. The monitor is passive: it never sends radio commands and never enables RX logging. Do not change radio settings during these tests unless a step says so.

Labels below are taken from the source: the Radio page card **Propagation Monitor** (Observe & diagnose group), the header indicator, and the **RF propagation monitor** section under Settings > Notifications.

## 0. Obtain and verify the candidate

1. Download the Windows candidate artifact for the 0.8.27 build being tested from its GitHub Actions run. Record the run link and artifact name: fill from the rc build being tested.
2. Extract it and verify both executables in PowerShell:

   ```powershell
   Get-FileHash .\Nightlink-Setup-*.exe -Algorithm SHA256
   Get-FileHash .\Nightlink-Portable-*.exe -Algorithm SHA256
   ```

   Expected Setup SHA-256: fill from the rc build being tested. Expected Portable SHA-256: fill from the rc build being tested. Do not continue if either differs from the release record for that build.
3. Export a Nightlink backup, quit through the tray (**Quit Nightlink and disconnect radio**), and install the candidate Setup over the current installation.
4. Record the companion radio name, model and firmware version shown on the Radio page.

## 1. RX-log availability

Nightlink does not enable RX logging. Signal (SNR/RSSI) and distance evidence depend on the firmware pushing RX-log events.

1. Connect the companion and wait for Ready.
2. Open the Radio page > **Receive log**. Leave it open for about 15 minutes with normal mesh traffic.
3. If rows appear, record "RX log available" and the time of the first row.
4. If no rows appear, the page shows "No RX-log observations yet. Leave the radio connected; silence does not establish a link failure." Record "RX log not observed" and the firmware version.
5. Open the Radio page > **Propagation Monitor**.
   - Pass with RX log available: no RX-logging warning is shown after RX-log rows arrive.
   - Pass with RX log not observed: the panel shows "RX logging off: monitoring limited. Nightlink does not enable RX logging. Only decoded messages and adverts are observed, so signal and distance evidence may be unavailable."
6. Continue the remaining tests either way, and record which RX-log condition applied.

## 2. Passive operation

Purpose: confirm the monitor adds no transmissions.

1. Note whether the companion sends automatic adverts and at what interval, if known. Automatic adverts are the radio's own behavior, not the monitor's.
2. Nightlink does not currently display the radio's sent-packet counter (radio.js reads it, but no screen shows it). If another trusted tool can read the companion's sent-packet count, record it before and after 1 hour idle with **Enable monitoring** on and no messages sent, then repeat for 1 hour with monitoring off. If no such tool is available, record "transmit count not measured".
3. Optional cross-check with a second radio in range running RX log: during the idle hour, record any packets from the companion other than its scheduled adverts.
4. Pass: no transmission attributable to the monitor. A count increase that matches scheduled adverts alone is a pass; record it with the interval.

## 3. Learning the baseline

1. With monitoring enabled and the radio connected, observe the header indicator and the panel's CURRENT STATUS.
2. Pass: while fewer than 24 covered hours exist (default `minBaselineHours`), the indicator reads **Learning baseline** and the panel explains "Collecting baseline; not enough history for reliable detection." No amber or red alert appears.
3. Disconnect the radio for at least 1 hour, then reconnect. Record **Baseline hours** before and after. Pass: the disconnected hour is not added to **Baseline hours**, and the indicator does not report an alert because of the gap.
4. Record the local time when the status leaves Learning baseline.

## 4. Normal operation for 48 hours

1. Leave the companion connected with normal use for 48 hours after learning completes.
2. Expected: the indicator reads **RF normal** most of the time and no alerts appear on ordinary days.
3. Record every alert (**Possible RF Opening** or **Strong RF Anomaly**) as a false-positive candidate: local time, panel CURRENT STATUS, **Confidence**, the full Evidence tiles, the Recent observations rows marked in "Flagged because", and a screenshot of the panel.
4. Note any concurrent known cause: a busy local event, new nodes joining, antenna or location changes, firmware updates.
5. Pass criterion for this test is recorded evidence only. The owner decides in test 10 whether the observed alert rate is acceptable.

## 5. Routing and identity assumptions

These checks test assumptions the detector relies on and that are not confirmed from firmware documentation. Record any mismatch as a failure of that assumption, with a screenshot of the Recent observations row and the matching contact.

1. Advert originator key. When a known contact advertises, find its row in Recent observations. Pass: the **Station** value matches the start of that contact's full public key (compare in the contact card), not a different key.
2. Direct versus forwarded.
   - For a neighbour known to be heard directly (no repeater in between), pass: its rows show **Reception** "Direct".
   - For a node known to be reached only through a repeater, pass: its rows show "Forwarded" with a hop count, for example "Forwarded · 2 hops".
   - Fail if a repeater-only node shows "Direct", or a direct neighbour shows "Forwarded".
3. Unknown path length. If any row shows **Reception** "Unknown", record its source and time. Pass: no row with an unknown or 0xFF path length is shown as "Direct", and its **Distance** reads "Unknown".
4. Distance. Pass: **Distance** shows a value only for "Direct" rows from stations with a known location, and reads "Unknown" otherwise.

## 6. Switching radios

1. Note the panel state, **Baseline hours** and Event history for SNOMAN HQ.
2. Connect the owner-designated V4 radio instead. Pass: its panel starts from its own history (Learning baseline if new); SNOMAN HQ events and baseline hours do not appear.
3. Switch back to SNOMAN HQ. Pass: its earlier baseline hours and event history are present, and no new alert appears at the moment of switching back.

## 7. Restart persistence

1. Record **Baseline hours** and the newest Event history entry.
2. Quit through the tray (**Quit Nightlink and disconnect radio**), reopen Nightlink and reconnect.
3. Pass: **Baseline hours** and Event history are restored. Past alert windows appear as history, not as an active alert. If an alert was active at quit, it does not reappear as active without new qualifying evidence.

## 8. Settings

Open Settings > Notifications > **RF propagation monitor**. Record the status line after each change ("Propagation settings saved." or "Propagation settings could not be saved.").

1. **Enable monitoring** off: pass when the indicator reads **Monitor off** and the panel states "Monitoring is turned off in Settings." Turn it back on.
2. **Alert sensitivity** (Low, Medium (recommended), High) and **Baseline period** (14 days, 30 days (recommended), 60 days): pass when each choice persists after reopening Settings and after restart.
3. **Show status indicator** off: pass when the header indicator is hidden; turn it back on.
4. **Alert animations** off: pass when alerts show without pulsing or flashing. With Windows reduced motion (or Nightlink's reduced-motion option) on, pass when no animation plays even if **Alert animations** is on.
5. **Alert sound** and **Windows notification** (both off by default): if a strong anomaly occurs while on, pass when one cue or notice appears per alert, none during quiet hours, and Windows notification settings are respected. Record "not triggered" if no strong anomaly occurs.
6. **View recent alerts** opens the Event history. **Clear alert history**: pass when "Alert history cleared." appears and history is empty.
7. **Reset baseline…**: pass when a confirmation (**Confirm baseline reset** / **Cancel**) is required, Cancel changes nothing, and confirming shows "Baseline reset. Learning starts again." and returns the status to Learning baseline.

## 9. Responsiveness

1. During tests 4-8, use messaging normally: channel messages, DMs, opening and closing the Propagation Monitor panel, and keyboard navigation inside it.
2. Pass: no noticeable delay in sending, receiving or switching conversations compared with monitoring off, and no UI stalls. Record any delay with time and what was open.
3. Record whether keyboard focus inside the open panel is lost while it refreshes.

## 10. Owner scope decisions

Record one decision per row, in the owner's words, before stable release preparation. These are not approvals until recorded by the owner.

| Area | Options |
| --- | --- |
| Default state | Ship monitoring on by default, or off by default and labeled Experimental |
| Alert thresholds | Keep Medium defaults, or adjust after the test 4 false-positive log |
| Unconfirmed assumptions (test 5) | Ship with assumptions disclosed, or hold until confirmed |
| RX log not available on tested firmware | Ship with "monitoring limited" disclosed, or hold |
| Any failed test above | Fix and rebuild, or disclose |
