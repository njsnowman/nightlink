# Nightlink 0.8.26-rc.6 - Remote read diagnostics candidate

Tracking [#109](https://github.com/njsnowman/nightlink/issues/109), [PR #110](https://github.com/njsnowman/nightlink/pull/110).

Adds an in-memory connection diagnostic view for selected remote devices: request phase, companion/server times, accepted route mode and reply budget, and inbound message type/length. Passwords, command values and reply contents are excluded. The trace clears on connection reset and is not persisted or exported. This builds on rc.5 timing corrections; it does not claim that the remaining physical read timeout is resolved.

Physical rc.5 evidence: administrator login succeeded; full inspection then failed on the first name field. A single manually separated get-name command had succeeded in the previous candidate. No settings or passwords were changed. The purpose of rc.6 is to compare those paths with minimal metadata and identify the remaining cause.

## Validation and physical diagnosis

Source `dba6a9e08fc57cf76d4e8cc33365cb244f56d40c`: 279 unit tests passed; rendered source and packaged Device Center checks passed; all 197 packaged assets matched source. [GitHub run 40980839536](https://github.com/njsnowman/nightlink/actions/runs/40980839536) passed both jobs. Local silent installation returned exit code 0 and installed version rc.6 was verified.

On hardware, login and six setting reads succeeded (name, TX power, coordinates, owner information and RX gain). The next optional path-hash request was accepted for a direct route with an estimated reply timeout of about 2.1 seconds, but no CLI reply was observed before the 30-second client deadline. No values were changed. This identifies the blocking step, not whether its missing reply was caused by firmware support or radio loss. The all-or-nothing inspection discarded successful core reads; rc.7 separates core radio inspection from optional queries.
